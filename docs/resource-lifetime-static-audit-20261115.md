# H1 PVZ 资源生命周期静态审查（2026-11-15）

> 此文保留修复前审查结论。四项已在后续修复完成，结果与真机证据见 [资源生命周期修复](resource-lifetime-fix-20261115.md)。

基于已安装程序 `10de8fc168694898eaceaeedd1b3e1eed3cd03f04e14745b70622ee8dde607fe` 对应的当前源码。检查了场景切换、动画库、领奖光效、加载页、暂停快照、音频及后台存档。此次没有修改运行代码、没有刷机或重新启动真机测试；资产数据只在电脑上解析，真机数值复用上一轮已保存的记录。

结论：仍有三处明确的资源持有时间过长，另外有一处后台保存的并发回收风险。不能把这些全部称为跨关卡、无限增长的内存泄漏。

## 1. P1：保存线程遍历与前台释放未形成互斥

位置：`runtime/async_save.h:99` 的 `save_next_job()` 与 `runtime/async_save.h:149` 的 `save_collect()`。

工作线程先将 `save_jobs[i]` 复制到局部指针 `j`，随后读取 `j->state`、`j->sequence`；前台同时可以把一个 state=3 的槽清空并 `free(job)`。两边只有 volatile 和内存屏障，没有保护整个“取得指针→读取字段”区间的互斥。

可构造的时序：工作线程取得一个已完成任务的指针，尚未读取字段时被前台抢占；前台回收并可能重用该块内存；工作线程恢复后继续读取旧指针。`__sync_synchronize()` 能约束读写顺序，不能延长对象寿命。这是静态可证明的悬空读取窗口，尚未在真机复现为某次崩溃。已有退出记录中的前台优先级 10、保存线程优先级 11 也符合前台可抢占保存线程的条件。

修复方向：队列扫描、任务认领及已完成任务摘除使用同一临界区或明确的完成队列协议；锁外执行文件操作和实际释放。不能只在 `free()` 外包一层锁，因为工作线程可能已经拿到了旧指针。

## 2. P1：开局就展开整包通关领奖光效

位置：`platform/source_patches.py:105` 的 StartPlaying 注入、`:112` 的继续游戏注入，以及 `platform/graphics/RewardEffects.cpp:54` 的 `Load()`。

每次进入游戏/继续存档都会 `H1RewardEffectsPrepare()`。它把整个 `reward-effects.h1re` 展开到 heap pages，并为两类效果分配最大帧缓冲。实际接管条件却是种子卡领取且 Board 已进入淡出，或专门创建的领奖星芒；普通种植和收阳光用不到整包。

当前离线包：文件 934,748 字节，展开数据 1,220,539 字节，调色板 1,220 字节，H1 页指针表 1,192 字节，两块帧缓冲 30,328 / 4,891 字节，合计 **1,258,170 字节**。此数不包含分配头、内存池余量和静态结构。它会在整场普通战斗期间占用约 1.26 MB。

修复方向：离线输出可按帧定位的目录和独立帧块，仅保留必要目录及播放工作区；在末波/奖励准备阶段完成预读，确保领取点击前就绪。避免把加载重新推迟到用户点击领取的瞬间。

## 3. P2：进入领奖页后，上一关战斗动画和草坪仍驻留

位置：`platform/source_patches.py:69` 的 ShowAwardScreen 注入、`:116` 的 MakeNewBoard 清理；`platform/actors/ActorPose.cpp:1135` 的帧结束处理。

ShowAwardScreen 切换图片所有权并释放 RewardEffects，却没有释放 ActorPose 库和 EarlyLawn。帧结束处理只退还不再使用的解码页，压缩块、目录、调色板等仍保留。它们要等创建下一块 Board、回菜单或退出才整体释放。AwardScreen 的种子卡使用 CachedFrames，不能因此把所有 CachedFrames 一并无条件清掉。

已有真机记录佐证（均为解码页保留数 0 的领奖页）：

| 记录 | 战斗动画库剩余字节 | 草坪剩余字节 | 合计 |
| --- | ---: | ---: | ---: |
| fixed-chain-15.json | 2,580,079 | 615,532 | 3,195,611 |
| fixed-chain-40.json | 3,032,189 | 771,180 | 3,803,369 |

因此领奖页确实可以留着约 **3.2～3.8 MB** 已结束战斗的数据，并与奖励页图像/音乐叠加。此项与第 2 项处于不同阶段，不能把两项数字当作同一时刻的总节省量。

修复方向：在 Board 完成处置、无绘制借用之后，结束其战斗库和草坪所有权，再准备领奖页；保留领奖页实际借用的卡片预览。回收过程也应纳入现有加载/音频服务阶段，避免制造新的界面停顿。

## 4. P2：已完成的保存任务仍保留整份数据副本

位置：`runtime/async_save.h:117`、`:139`、`:149`、`:179`。

工作线程完成后只把任务标为 state=3；常规逐帧 `pvzh1_save_service()` 不调用回收。`save_collect()` 只由后续提交、文件依赖等待或关闭路径调用。若保存完成后停留在不再发生文件访问的菜单，任务和整份存档副本会继续占用堆。

普通保存允许最多 512 KiB 的 payload，4 个槽的结构性上限约为 2 MiB 加任务头；这不是本次已经实测到的占用量。实际大小取决于保存内容，常见为数十至数百 KB。

修复方向：先解决第 1 项的任务寿命同步，再让前台帧服务及时回收完成任务。不要让文件工作线程直接调用应用的 C++/newlib 分配器。

## 未列为缺陷的检查项

- Loading 背景和 inflater 在首帧后释放，进度条补丁在 loading_end 释放。
- 暂停快照在恢复游戏的首帧或 Board 销毁时释放。
- 首次开场电影有自然结束和 Board 销毁的释放路径，上轮真机记录也确认结束后归零。
- 文字/绘制计划有场景退出和源图失效清理。
- 音乐切换会更新共享模块引用；开场预读的 hugewave/siren 也会用于普通关卡的大波次，不能仅凭其跨开场保留就断言泄漏。
- 循环动画当前解码工作集、共用选项 UI、分配器可回收的空页没有计入“遗忘释放”。

建议顺序：先补保存队列同步与完成回收，再处理常驻奖励整包和领奖页战斗资源退出边界。所有修复仍需定向回归和真机验证；这份审查不冒充新的真机测试结果。
